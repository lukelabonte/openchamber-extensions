# FirstMate feature comparison

Compared local FirstMate at `38df9cd3293435cf0c6b1a76462a296b9e7863a5` with [`gpambrozio/bb-plugins/firstmate-crew` at `f2d8491208978f13a245f46a34cc195338173c0e`](https://github.com/gpambrozio/bb-plugins/tree/f2d8491208978f13a245f46a34cc195338173c0e/firstmate-crew). Date: 2026-10-13. This is a source comparison, not a runtime validation. No production code was changed.

The local version already has the core delegation loop. The gaps are mostly richer task records and decisions, durable watch delivery, coordinator lifecycle controls, and upgrade handling. The linked version is the bb port, not the older Paseo plugin referenced by the local spec. [Local charter](../../firstmate/templates/charter.md), [upstream README][upstream-readme]

## Richer agent policies, not enforced plugin automation

The linked plugin's charter has behavior the local default charter doesn't spell out. These are shipped instructions, not proof that a background controller guarantees compliance.

- **Approval tied to an exact PR head.** Store the reviewed head, recheck OPEN/CLEAN/required checks, refuse a moved head, merge with `--match-head-commit`, and confirm MERGED. Local landing instructions require commit/CI/scope evidence but don't define this exact-head protocol. [Upstream merge policy][delivery-policy], [local shipping](../../firstmate/templates/charter.md#L22-L34)
- **Relayed requests aren't merge approval.** Add a durable per-task hold that overrides `+yolo` until approval arrives in the supervisor chat. Local tasks have no hold field or equivalent handoff-origin policy. [Upstream relay policy][relay-policy], [local schema](../../firstmate/service/backlog.ts#L15-L25)
- **Explicit recovery and restart reconciliation.** Reconcile live crew and PR state with records, distinguish manual stops from lost-host/setup/queued-send failures, and follow a bounded inspect/answer/correct/relaunch ladder. Local code already detects failures, blocked states, and a cautious 30-minute stall; it doesn't implement that recovery ladder. [Upstream reconciliation][reconciliation], [recovery][supervision], [local stall detection](../../firstmate/service/poller.ts#L564-L628), [local event summaries](../../firstmate/service/poller.ts#L651-L663)
- **Permission-aware supervision.** Upstream instructions approve routine in-worktree actions, deny actions outside the worktree, and escalate sensitive ones. The local service instead attempts to set worker permissions to automatic approval. The upstream distinction depends on agent compliance and bb's interaction APIs; it isn't a code-enforced permission classifier in FirstMate. [Upstream policy][supervision], [local permission mode](../../firstmate/service/permissions.ts#L4-L10)
- **First-class investigation workflow and learnings.** Separate Ship from Scout, reuse existing findings, preserve scout reports and fleet learnings, require bug-reproduction evidence, and promote an investigation after implementation is authorized. Local briefs/reports can hold investigations, but there are no shipped task-kind fields, learnings file, or equivalent intake/finishing policy. [Upstream intake][intake], [records][upstream-records], [finishing][finishing], [local provisioning](../../firstmate/service/provision.ts#L32-L39), [local charter](../../firstmate/templates/charter.md)
- **Acting on approved watch findings.** Upstream instructions route maintainer reviews and red checks back to workers and reconcile merged/closed PRs. The local charter treats watch findings as information to act on only when the captain asks. Neither plugin implements that full response policy as a background state machine. [Upstream supervision][supervision], [local watch policy](../../firstmate/templates/charter.md#L40-L42)

## Deliberate design and host differences

- **One supervisor across projects versus one per project.** Upstream resolves projects under one first mate and presents one fleet. Local ADR-0001 deliberately isolates each project's coordinator/home/backlog; cross-repository tasks must be split by hand. This isn't an unfinished local implementation. [Upstream README][upstream-readme], [local ADR](../../docs/adr/0001-one-first-mate-per-project.md#L9-L20)
- **Native every-turn child notifications versus extension polling.** Upstream relies on bb to deliver child completion/failure/attention messages with the last message and interruption/setup reasons. Local polling sends event summaries, with full changed assistant text forwarded specifically after a board steer. The upstream host contract wasn't runtime-tested in this comparison. [Upstream host description][host-supervision], [charter supervision][supervision], [local forwarding](../../firstmate/service/poller.ts#L314-L321), [event messages](../../firstmate/service/poller.ts#L641-L663)
- **Remote worker placement.** bb can choose among configured checkouts/hosts. Local FirstMate targets an OpenChamber project directory and local worktrees. Treat multi-machine workers as a host/integration difference, not a missing panel button. [Placement][placement], [upstream limits][integration-limits], [local dispatch](../../firstmate/templates/charter.md#L17)
- **End and cleanup have different semantics.** Upstream End archives a host thread and its worktree is later retired by bb. Local End only archives the card, preserving the session/worktree; landed-work cleanup stays with the captain. Copying upstream behavior would weaken that preservation boundary. [Upstream controls][crew-controls], [local End](../../firstmate/service/main.ts#L928-L930), [local cleanup](../../firstmate/templates/charter.md#L36-L38)
- **Landing authority has different implementation boundaries.** Upstream allows its coordinator to perform approved/local/`+yolo` merges. Local FirstMate always dispatches a landing worker and never grants the coordinator repository-mutation authority. [Upstream delivery policy][delivery-policy], [local ADR](../../docs/adr/0002-coordinator-never-writes-to-managed-repos.md#L11-L19)

## Already present or not established as gaps

Isolated workers, seven board states, PR links, open/steer/interrupt/relaunch/end controls, scheduled custom watches, silent-run behavior, watch toggles, failure suppression, shipping modes and `+yolo`, suggestions with send/dismiss and duplicate protection, editable standing orders, and catch-up reports already exist locally. Local watches also have create/schedule-edit/run-now controls, and the board has supervision-health and cautious stall warnings. [Local charter](../../firstmate/templates/charter.md), [routes](../../firstmate/service/main.ts#L1236-L1294), [local stall indicator](../../firstmate/service/board.ts#L43-L65)

Don't import the older local spec's out-of-scope list as evidence of gaps against this linked repository. This bb plugin uses the host's native Files and chat rather than shipping a separate file editor/chat. Second mates, away mode, X/Discord relays, a context-fullness ring, and a no-mistakes pipeline weren't established as capabilities of the linked version by this investigation. [Upstream README][upstream-readme], [local spec](../firstmate/spec.md#L70-L85)

## Code-backed capabilities

| Capability | What the implementation provides |
| --- | --- |
| Supervisor lifecycle | Launch a pinned first mate in a registered FirstMate home project. Adopt an existing thread only when its workspace matches the home, including through symlinks. Serialize launch, adoption, restart, and release to avoid overlapping lifecycle changes. Release forgets the supervisor without archiving it or its crew. [Lifecycle][lifecycle] |
| Context management | Compact through bb's native API. Restart clears context on the same thread, rereads the opening, and retains the child-thread relationship. Both refuse a supervisor that's mid-turn. Restart and release have UI confirmation dialogs. [Server][context], [UI][settings-ui] |
| Isolated dispatch | `bb firstmate-crew crew spawn` checks the caller's thread ID against the stored first mate. It reads a brief file, resolves an exact project name or ID, starts a child thread, and records task/kind/project metadata. A new managed worktree is the default. `--environment` reuses an existing environment. [Dispatch][dispatch] |
| Worker placement and model choice | Prefer a project checkout on the bb server's machine, otherwise its default or first checkout. Apply configured crew provider/model/reasoning, with per-spawn overrides. Provider/model flags must appear together. The SDK adapter validates reasoning levels. [Placement][placement], [Model defaults][model-defaults], [Settings][settings] |
| Cross-thread handoff | `tell` accepts shell words or strict base64 UTF-8. The base64 path preserves multiline text, limits decoded requests to 12,000 bytes, and removes the heredoc's added newline. Every relay gets a plugin-generated origin line with the claimed thread and available project/branch. Delivery joins an active turn rather than interrupting it. [Relay][relay], [Delivery][ask] |
| Crew board | Join live child threads with Markdown backlog items. Show Queued, Working, Blocked, Parked, Done, Failed, and Idle, status lines, PR links, dependencies, pending interaction counts, and task facts. A worker's `done:` line doesn't make its task Done. [State rules][columns], [Cards][cards] |
| Board layout and refresh | Hide empty columns. Persist folds and column order in browser local storage. Refresh on fleet events, realtime reconnection, and a configurable poll, default 10 seconds. Retain the last board with an error notice after a failed refresh. [Layout][board], [Refresh][refresh], [Failure notice][refresh-error] |
| Worker controls | Open thread, steer directly, interrupt, ask the first mate to relaunch, and archive through End. Server actions reject threads outside the stored first mate's children. End requires confirmation unless the joined backlog item is Done. Relaunch is a message to the agent, not a server-side recovery engine. [Controls][crew-controls], [Relaunch template][relaunch] |
| Worker-specific panel | A worker's thread shows its own card and a note box that sends context to the first mate without steering the worker. Unrelated threads offer adoption or navigation to the supervisor. [Worker panel][worker-panel], [Panel routing][panel-routing] |
| Captain decisions | Parse backlog actions into answer buttons. Held cards also have a free-text Answer box. Answers include task identity and navigate to the first mate after delivery. These buttons send prompts, not direct merge operations. [Decision UI][decision-ui] |
| Suggestions | Send a suggested request, then remove its card only after delivery succeeds. Expand clipped requests for reading or copying without sending. Trash records a dismissal and suppresses matching prompts after whitespace normalization. Keep the newest 50 dismissals. A shared client send gate prevents overlapping button sends across tab changes. [Suggestion UI][suggestion-ui], [Dismissals][dismissals], [Send gate][send-gate] |
| Durable home and opening | Seed captain orders, projects, backlog, suggestions, learnings, and opening only when missing. Render `AGENTS.md` from the charter. Keep operations attached to the active supervisor's home even if the home setting changes. [Home][home], [Active home][active-home] |
| Charter upgrades | Fingerprint the charter. Update untouched copies automatically. Preserve edited copies and write `data/charter.new.md` when upstream changes. Board Compare opens that file. Done acknowledges the new baseline without replacing the user's wording. [Upgrade logic][charter-upgrades], [Compare UI][charter-ui] |
| Native host integration | Register a FirstMate thread tab, settings section, and command-palette entries for Open and Bearings. Use bb's native chat, thread navigation, files, compaction, and archive APIs. [App registration][app], [SDK adapter][sdk-actions] |

## Implemented automation

| Capability | What runs without an agent deciding to run it |
| --- | --- |
| Custom scheduled watches | Discover executable, non-symlink scripts in the home's `watches/` folder. Require a shebang and a schedule comment in the first 20 lines. Parse classic five-field cron plus `@hourly`, `@daily`, and `@weekly`. Supply home/backlog/watch-name/per-watch-state environment variables. Invalid watches stay visible but don't run. [Discovery][watch-discovery], [Schedule][schedule], [Execution environment][watch-environment] |
| Bounded execution | Two-minute run timeout. Don't overlap runs of the same watch. Stop process groups with SIGTERM and a later SIGKILL. Cap output and retained stderr. Report a recurring execution failure once until a run succeeds. Silent successful runs don't send an agent message. [Runner limits][watch-limits], [Recording][watch-recording], [Process handling][process-handling] |
| Persistent idle delivery | Persist watch results and pending notes. Hold notes while the first mate is absent or busy. Send one batch with `queue-if-active` once it's idle. Keep at most 20 queued notes, clip each output to 16,000 characters, and target a 32,000-character batch. Drop oldest whole notes and report the count. Serialize flushes and drain the runner on reload. [Queue and flush][watch-queue], [Delivery][watch-delivery], [Reload lifecycle][watch-lifecycle] |
| Watch controls and history | Show schedules, enabled state, invalid/failing/outdated status, last run, and expandable last output. Toggle watches individually and open their scripts. | Built-in PR watch | Every five minutes, inspect GitHub PR URLs in non-Done backlog sections, including other owners' repositories. Baseline new PRs silently. | PR polling and script upgrades | Four concurrent PR lookups, 20-second lookup timeout, default 70-second budget, and least-recently-checked ordering. ## Prompt and skill workflows, not enforced orchestration

These capabilities live in the charter or skill. The plugin provides supporting records and host operations, but an agent must follow the instructions.

- **User-triggered `/fm`.** Forward the user's exact request through a quoted heredoc and base64 stdin. Don't perform the work in the originating thread. Ask for text when empty. Stop after a failed send. `disable-model-invocation: true` is skill metadata whose enforcement depends on the harness. [Skill][fm-skill]
- **Delegation and safety policy.** First mate writes only in its home. Workers don't merge, push the default branch, address the captain, or create more workers. Captain authority covers destructive changes, discarded work, scope expansion, credentials, and publishing. The charter calls these hard rules, but they're instructions to agents. [Supervisor rules][hard-rules], [Worker brief][worker-brief]
- **Delivery modes and merge checks.** `direct-PR`, `local-only`, and `reviewed-PR`, with `reviewed-PR` as the unregistered-project default. `+yolo` allows limited standing merge authority. Before merging, compare the approved review head, OPEN/CLEAN state, and required checks. Use `--match-head-commit` and confirm MERGED afterward. No plugin merge controller enforces this sequence. [Delivery policy][delivery-policy]
- **Relayed-request authority hold.** Relays may start or steer work but don't count as captain approval. Record a durable merge hold that overrides `+yolo` and standing orders until the captain approves in the supervisor chat. Code always prefixes relays. The hold and approval interpretation remain agent responsibilities. [Relay policy][relay-policy]
- **Restart reconciliation and intake.** Read captain orders, registry, backlog, live projects/crew, and PR states. Repair records against live evidence. Reuse existing findings. Distinguish Ship from Scout, preserve investigation reports, require bug reproduction evidence, and dispatch independent work without a concurrency cap. [Reconciliation][reconciliation], [Intake][intake]
- **Recovery and permissions.** Inspect status, logs, and pending interactions. Respect manual stops. Handle lost-host interruptions, setup failures, and queued-send failures separately. Answer routine worker questions, escalate risky permissions, and use a bounded stuck-worker ladder ending in same-worktree relaunch. These decisions aren't a background state machine in the plugin. [Supervision][supervision]
- **Finishing and Bearings.** Validate PR/report artifacts, preserve unlanded work, archive only after landing, unblock queued tasks, and keep suggestions current. Bearings has four fixed sections and optional dated status-report output. The button sends a request; the agent builds the report. [Finishing][finishing], [Bearings][bearings]

## Claim boundaries

- Package version is 0.5.0. It requires bb >=0.46 and plugin SDK >=0.6.37. These are bb integrations, not OpenChamber implementations. [Manifest][manifest]
- Child completion, failure, interruption, and attention notifications are attributed to bb. The plugin's event listeners refresh the board and flush watches; they don't implement that parent-notification machinery. Host notification behavior wasn't independently exercised. [Host description][host-supervision], [Listeners][listeners]
- Home and watches run on the bb server's machine while bb is running. Worker environments may use another configured host. Missed watch minutes aren't replayed. [Limits][integration-limits], [Schedule][schedule]
- Watch scripts inherit the server environment and execute as ordinary processes. File confinement protects plugin-owned reads/writes, not arbitrary scripts or agent shell commands. The implementation also documents check/use and final-check/rename race windows. [Environment][watch-environment], [Filesystem boundaries][file-boundaries], [Rename window][file-race]
- Caller thread identity on relays is explicitly a sender claim. End's plugin-side safety gate checks backlog Done or confirmation, not independent proof that Git work landed. Serialized watch delivery doesn't establish exactly-once delivery across process crashes. [Relay][relay], [End][crew-controls], [Flush][watch-queue]

This inventory supports the comparison above; implementation and agent-guidance claims remain separate.
